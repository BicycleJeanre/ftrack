# Import And Export

## 1.0 Purpose

1.1 Explain how to export your FTrack data to a JSON file and import it again.

## 2.0 Where Your Data Lives

2.1 FTrack stores app data in browser storage.

2.2 Export is the primary way to create a portable backup.

## 3.0 Export Data

3.1 Use the navbar button Export Data.

3.2 Or use the shortcut.

3.2.1 Mac Cmd+E.

3.2.2 Windows Ctrl+E.

3.3 Your browser downloads a JSON file named like.

3.3.1 ftrack-backup-YYYY-MM-DD.json.

## 4.0 Import Or Upgrade Data

4.1 Use the navbar button Import Data.

4.2 Or use the shortcut.

4.2.1 Mac Cmd+I.

4.2.2 Windows Ctrl+I.

4.3 Select a JSON export file. The in-app Data Upgrade Review checks a copy of
the file before changing your browser data.

4.4 Review the result.

4.4.1 The review shows the source and schema-version change.

4.4.2 Validation must pass before import is enabled.

4.4.3 What Changed groups every added, changed, or removed field and explains
why it changed.

4.4.4 Historical Migration Notes identifies records retained by earlier
migrations. These notes are an audit trail, not current validation failures.

4.4.5 Download Change Report saves the complete machine-readable audit.

4.4.6 Download Upgraded JSON saves the prepared current-schema data without
importing it.

4.5 Select Import Upgraded Data or Import Validated Data only after reviewing
the result.

4.5.1 Import replaces your current data.

4.5.2 The app reloads after a successful import.

## 5.0 Check Current Browser Data

5.1 Select Data Check in the navbar.

5.2 Select Current Browser Data.

5.3 FTrack analyzes the raw JSON in browser storage without replacing it.

5.4 If an older schema is found during startup, FTrack opens the same review
before loading the data.

5.5 The original browser data remains unchanged until you select Apply Upgrade
to Browser Data.

5.6 If validation finds legacy values that can be normalized without losing
information, select Preview Safe Repairs.

5.6.1 The preview lists every proposed change in What Changed and validates the
repaired copy before enabling Apply Safe Repairs to Browser Data.

5.6.2 Safe repairs cover unambiguous data-type normalization, such as numeric
IDs or amounts stored as numeric strings. They can also reconstruct required
legacy metadata when the saved data provides one deterministic answer: a
missing account currency from the single currency used by the surrounding app
data, an empty transaction description from its account names, and missing
Yearly recurrence month/day values from its saved start date.

5.6.3 Safe repairs do not invent amounts, choose between conflicting currencies,
rewrite ambiguous records, or alter retained recovery records.

5.6.4 Historical notes are limited to 100 visible entries for readability. The
downloadable change report retains the complete audit.

5.7 If validation passes but recoverable recurring-link notes remain, select
Resolve Recurring Links.

5.7.1 These notes describe recovery actions that were already applied, such as
preserving an occurrence as manual when its recurring identity was ambiguous.

5.7.2 FTrack relinks an occurrence only when the original recurring rule is
unique, the recovered date is generated by that rule, the manual occurrence is
unique, and the resulting occurrence identity does not collide.

5.7.3 Records that cannot pass every check remain visibly unresolved. They are
not removed or marked resolved automatically.

5.7.4 The preview report embeds the original migration report and every applied
relink for auditability.

5.8 If recovered transactions cannot be relinked automatically, select Review
Transactions in Historical Migration Notes.

5.8.1 Review pages show the transaction description, scenario, date, status,
amount, and account movement. Up to 25 records are shown per page.

5.8.2 Select Confirm Manual when the transaction is an intentional standalone
budget entry. The occurrence remains unchanged and its recovery note is closed.

5.8.3 Select Remove Transaction when the recovered occurrence should not exist.
The occurrence is removed only after the decision preview is applied.

5.8.4 To reconnect a transaction, select a recurring rule and scheduled date,
then select Link to Recurrence. FTrack accepts the link only when the rule
generates that date and the resulting occurrence identity does not collide.

5.8.5 Select Preview Decisions to revalidate the complete data set and review
every change before applying it. Unreviewed records and their notes remain
unchanged.

5.8.6 Applied decisions are appended to migrationReport.resolutionHistory with
the scenario, occurrence, decision, and resolution time. Link and remove choices
also mark saved projections stale so they are refreshed from the revised plan.

## 5.9 Statement Mapping and Actions

Retained statements belong to the scenario, not a primary account. Selecting a
CSV automatically retains its complete original text and rows. Select a budget
period (month, week, quarter, year or custom inclusive dates) for reconciliation.
Separate Transactions from / to dates control source eligibility without changing
the selected budget period. Monthly defaults are previous-month 25th through
selected-month 25th, inclusive; edit either date and Apply dates for early salary
cutoffs. Dates stay set per period while the dialog is open. View full source and
source/report downloads are in the top toolbar. The source is never trimmed.

Saved description, original-description, category or parent-category rules supply
both FTrack primary and secondary accounts and a default action. These budget
accounts need not be the bank account on the statement. Rules apply globally
within the scenario. Conflicting rules require review; no row is auto-approved.
Description conditions ignore bank references, long numbers, dates and common
payment prefixes. Category conditions retain their exact or contains semantics.

Actions use the account pair within the budget period, in either orientation and
without requiring the bank movement type to match FTrack. One statement row gets
Add actual + close plan; repeated rows for the pair get Add line item; no period
transaction gets Create period transaction. Existing blocked targets require
review rather than duplicate creation. Future-plan changes are manual; Ignore
preferences remain automatic. Budget amount shows the current plan value.
All suggestions remain overridable. Multiple targets require Choose payment.
Same-pair source rows accumulate as dated lines on that transaction; another
period uses another occurrence. An existing non-itemized actual is preserved as
an initial line. Recurring definitions and planned amounts stay unchanged.

Create period transaction + add to recurring plan asks for a repeat pattern and
saves the actual plus one recurring rule atomically. The rule uses the approved
total and starts after the current budget period; existing future rules are not
duplicated. Actual + update future plan affects the next segment, not earlier
history. Existing actuals are updated through the normal completion action;
there is no separate link-only choice. Legacy link-only audit records remain.
Source fingerprints
prevent repeated application, including line additions across retained files.

Override either account or action in a review row without changing its rule.
The save icon explicitly creates or updates a rule with the pair and action;
the view icon opens its saved rule. Original descriptions and categories remain
visible. Shared account pickers provide type/group filters, search and quick
account creation in review rows and mapping forms/grid editors. Save/view icons
are inline beside the secondary account; mapping/target details are hover text.
Source and review grids use standard sortable, banded tables; review
supports grouping and bulk approval.

Saved mappings use an editable grid with primary/secondary account, default
action and condition columns. Click a cell to edit; Escape cancels. Saves and
removals keep the section open. Select visible mappings for atomic bulk edits or
confirmed removal. Filters combine matching text and secondary account and stay
set after edits. Hidden rows are not included in bulk selections.

Search is case-insensitive contains matching: `*` matches zero or more
characters, `%` exactly one, `**` a literal star and `%%` a literal percent.
This syntax applies to grid search, not saved rule conditions. Rules are created
explicitly; there is no proposed-mapping feature.

Schema 45 data upgrades to 46: existing statement account links become retained
legacy metadata, and existing mapping account IDs become primary accounts.
Legacy action hints become default actions; missing hints default to line items.
Raw CSVs, rows and prior decisions are preserved. Data Check previews local/file
upgrades; integrity-verified older cloud snapshots are upgraded on load.

## 6.0 Clear Data

6.1 Use the navbar button Clear Data.

6.2 Confirm the warning.

6.3 The app reloads after clearing.

6.4 Export first if you want a backup.

## 7.0 Troubleshooting

7.1 Import is disabled.

7.1.1 Review the Validation section for malformed JSON, missing collections,
invalid references, or other current-schema violations.

7.1.2 Current exports use schemaVersion 46.

7.1.3 Older exports are upgraded in memory. Review What Changed, Warnings and
Recovery, and the downloadable change report before applying the result.

7.1.4 Future schema versions are not downgraded.

7.1.5 If Preview Safe Repairs is available, use it to prepare a valid copy and
review each change. The Import Upgraded Data button is enabled once the repaired
copy passes validation. Historical migration notes may remain visible; they are
audit records and do not disable import.

7.1.6 Any active validation issues still shown after the repair preview require
correction in the source data because FTrack cannot resolve them deterministically.

7.2 You hit storage limits.

7.2.1 Export your data.

7.2.2 Clear old scenarios.
